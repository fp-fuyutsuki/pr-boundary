# PR Boundary v0.1.0 Specification

Status: implementation-ready draft  
Working name: PR Boundary  
Primary form: GitHub JavaScript Action  
Secondary form: local CLI  
Language: TypeScript strict mode  
License: Apache-2.0

## 1. Product statement

PR Boundary fails a pull request when its actual changed paths exceed the repository-controlled scope selected for that PR.

The product is not an AI detector and is not limited to AI-generated pull requests.

It should work identically for:

- human contributors
- coding agents
- Dependabot
- Renovate
- other bots

The core model is:

```text
trusted base policy
        +
repository-controlled scope state
        +
actual PR diff
        ↓
deterministic verdict
```

## 2. Core trust property

The PR being evaluated must not be able to replace the policy used to evaluate that same PR.

GitHub mode therefore loads the policy from the exact PR base SHA.

The recommended workflow must also execute trusted workflow code. The v0.1.0 design uses a metadata-only pull_request_target workflow with contents: read, pull-requests: read, and statuses: write only; there is no PR checkout or execution.

## 3. Non-goals

v0.1.0 does not:

- judge code quality
- detect malware
- detect secrets
- detect whether AI wrote a PR
- interpret Issue text
- infer scope with an LLM
- run tests from the PR
- execute repository code
- automatically modify a PR
- post comments
- add or remove labels
- close PRs
- provide a hosted dashboard
- provide GitLab support
- implement OPA/Rego
- perform semantic import analysis

## 4. Canonical policy

Path:

`.github/pr-scope.yml`

Example:

```yaml
version: 1
label_prefix: "scope:"

profiles:
  docs:
    allow:
      - "README.md"
      - "docs/**"

  tests:
    allow:
      - "test/**"
      - "**/*.test.ts"
      - "**/*.spec.ts"

  ci:
    allow:
      - ".github/workflows/**"
    allow_protected: true

  policy:
    allow:
      - ".github/pr-scope.yml"
    allow_protected: true

protected:
  - ".github/workflows/**"
  - ".github/pr-scope.yml"
  - "CODEOWNERS"

defaults:
  no_profile: review
```

## 5. Policy schema

### 5.1 `version`

Required integer. v0.1.0 accepts only `1`.

Unknown versions are invalid policy.

### 5.2 `label_prefix`

Optional non-empty string.

Default:

`scope:`

A profile key is appended to this prefix.

Profile `docs` therefore maps to `scope:docs`.

Profile keys must be simple stable identifiers.

Recommended validation:

`^[a-z0-9][a-z0-9_-]{0,63}$`

### 5.3 `profiles`

Required object with at least one profile.

Each profile has:

- `allow`: non-empty list of glob patterns
- `allow_protected`: optional boolean, default `false`

No arbitrary code, expressions, custom YAML tags, or executable callbacks.

### 5.4 `protected`

Optional list of glob patterns.

Default empty list.

A path matching `protected` can pass only if:

1. the active profile's `allow` also matches the path; and
2. `allow_protected: true` on that profile.

`allow_protected: true` never bypasses the normal `allow` list.

### 5.5 `defaults.no_profile`

Enum:

- `review`
- `pass`

Default:

`review`

`review` -> no selected profile produces `REVIEW_REQUIRED`.

`pass` -> non-protected paths may pass without a profile; protected paths still require an explicit profile with `allow_protected: true`.

This exists as a migration mode.

## 6. Scope label selection

Let the configured prefix be `scope:`.

1. Collect current PR labels.
2. Find labels beginning with that exact prefix.
3. If none:
   - apply `defaults.no_profile`.
4. If any prefixed label maps to no configured profile:
   - `REVIEW_REQUIRED / UNKNOWN_SCOPE_LABEL`.
5. If more than one valid scope profile is selected:
   - `REVIEW_REQUIRED / MULTIPLE_PROFILES`.
6. Exactly one valid profile:
   - evaluate all changed paths against that profile.

No union of multiple profiles in v0.1.0.

The current label state is trusted as repository-controlled state. v0.1.0 does not audit the actor who applied the label.

## 7. Changed-file model

Canonical internal status:

- `added`
- `modified`
- `removed`
- `renamed`

For each ordinary change, evaluate `filename`.

For `renamed`, evaluate both:

- `previous_filename`
- `filename`

If either old or new path is unauthorized, the file change is unauthorized.

Unknown GitHub statuses fail closed as `REVIEW_REQUIRED / UNSUPPORTED_FILE_STATUS`.

## 8. Path validation

Paths are repository-relative POSIX paths.

Reject:

- absolute paths
- NUL
- `..` path segments
- malformed empty/ambiguous path representations

Backslash is not treated as a path separator for GitHub repository paths.

Local CLI normalizes Git output into canonical POSIX separators before evaluation.

Matching is case-sensitive.

Symlinks are not followed.

Submodules are not cloned.

## 9. Glob semantics

Use one documented glob implementation consistently.

Required behavior:

- patterns match the full repository-relative path
- `*` does not cross `/`
- `**` may cross directories
- dot-prefixed files/directories are matchable
- matching is case-sensitive

Policy patterns themselves must be validated and bounded.

No negated patterns in v0.1.0. Denial is expressed by lack of allow or protected handling.

## 10. File decision algorithm

For an active profile and path `p`:

```text
allowed = matches(profile.allow, p)
protected = matches(policy.protected, p)

reasons = []

if not allowed:
    reasons += OUTSIDE_SCOPE

if protected and not profile.allow_protected:
    reasons += PROTECTED_PATH

if reasons is not empty:
    BLOCKED
else:
    allowed
```

A path may therefore carry both `OUTSIDE_SCOPE` and `PROTECTED_PATH`. This is intentional: the first explains that the selected profile did not authorize the path, while the second explains that the path is additionally protected.

For rename:

```text
evaluate(previous_filename)
evaluate(filename)
```

Both must be allowed.

## 11. Verdicts

### PASS

All required inputs are complete and valid, and every changed path is authorized.

### REVIEW_REQUIRED

The tool cannot safely conclude that the PR is authorized.

Examples:

- no profile in strict mode
- multiple profiles
- unknown prefixed label
- missing/invalid policy
- GitHub API failure
- incomplete file list
- unsupported file status
- invalid path
- unsupported event

The policy verdict is enforced by the fixed `pr-boundary/scope` commit status on the exact PR head SHA. Operational failures and status publication failures fail the workflow; a normal evaluation may publish `error` or `failure` for `REVIEW_REQUIRED` or `BLOCKED` without requiring the workflow transport itself to exit non-zero.

### BLOCKED

The tool has complete inputs and has proven at least one changed path exceeds the selected scope.

Examples:

- outside allow list
- protected path without `allow_protected`

The policy verdict is enforced by the fixed `pr-boundary/scope` commit status on the exact PR head SHA. Operational failures and status publication failures fail the workflow; a normal evaluation may publish `error` or `failure` for `REVIEW_REQUIRED` or `BLOCKED` without requiring the workflow transport itself to exit non-zero.

## 12. Verdict priority

Known unauthorized change takes precedence over ambiguity only when the required evaluation inputs are complete enough to prove the violation.

Never turn a known violation into PASS.

Never turn unknown/incomplete input into PASS.

## 13. Stable reason codes

v0.1.0:

- `OUTSIDE_SCOPE`
- `PROTECTED_PATH`
- `NO_PROFILE`
- `MULTIPLE_PROFILES`
- `UNKNOWN_SCOPE_LABEL`
- `POLICY_UNAVAILABLE`
- `POLICY_INVALID`
- `CHANGED_FILES_INCOMPLETE`
- `INVALID_REPOSITORY_PATH`
- `UNSUPPORTED_FILE_STATUS`
- `GITHUB_EVENT_UNSUPPORTED`
- `PR_STATE_CHANGED`
- `INTERNAL_ERROR`

Reason codes are part of the machine-facing contract.

PR_STATE_CHANGED is returned when the fresh final PR snapshot differs from the run's captured head SHA, base SHA, or relevant scope labels.

## 14. GitHub Action event model

Recommended dedicated workflow:

```yaml
name: PR scope

on:
  pull_request_target:
    types:
      - opened
      - reopened
      - synchronize
      - labeled
      - unlabeled
      - edited
      - ready_for_review

concurrency:
  group: pr-boundary-${{ github.event.pull_request.number }}
  cancel-in-progress: true

permissions:
  contents: read
  pull-requests: read
  statuses: write

jobs:
  scope:
    runs-on: ubuntu-latest
    steps:
      - uses: OWNER/REPO@FULL_COMMIT_SHA
        with:
          github-token: ${{ github.token }}
```

Rationale:

- `pull_request_target` executes trusted base-repository workflow code instead of the PR merge workflow.
- The scope gate needs metadata and base-revision policy, not execution of PR code.
- The workflow explicitly limits `GITHUB_TOKEN` to metadata reads and the single commit-status publication permission.
- The workflow uses no secrets, no OIDC, no environment, no checkout, and no PR-controlled shell code.

The fixed commit-status context is `pr-boundary/scope`. The workflow publishes `pending` to the captured exact PR head SHA as soon as the fresh snapshot is available. Final mapping is `PASS -> success`, `REVIEW_REQUIRED -> error`, and `BLOCKED -> failure`. A status publication failure fails the workflow; it must never be represented as a successful log-only evaluation.

The final status is published only for the SHA captured by that run. If a fresh final snapshot shows that head SHA, base SHA, or relevant scope labels changed, the run must not publish `PASS`; it ends with `PR_STATE_CHANGED` and `REVIEW_REQUIRED`. It must not write a status to the newer head SHA. The new event run owns evaluation of the new head. The remaining publication race is a documented limitation.

This is a deliberately constrained use of `pull_request_target`.

Documentation must warn users not to add PR-head checkout/build/test steps to this privileged workflow.

## 15. GitHub policy loading

From event/API obtain:

- owner
- repo
- PR number
- exact `base.sha`
- exact `head.sha`
- current labels
- expected `changed_files` count

Fetch `.github/pr-scope.yml` from the repository at the exact `base.sha`.

Do not read the workspace copy.

Record in result:

- `base_sha`
- `head_sha`
- policy object/blob identity if available
- selected profile

## 16. GitHub changed-files completeness

Use GitHub's Pull Request "List files" REST endpoint with pagination.

Fetch up to API maximum using `per_page: 100`.

GitHub documents a maximum response of 3000 files.

Compare the number of retrieved changed-file records with the pull request's expected `changed_files` count.

If completeness cannot be proven:

`REVIEW_REQUIRED / CHANGED_FILES_INCOMPLETE`

A PR with `changed_files > 3000` must never PASS. Exactly 3000 files may be evaluated only when all 3000 records are retrieved and the expected count matches exactly; otherwise the result is `REVIEW_REQUIRED`.

## 17. Untrusted output

PR-controlled data includes:

- filenames
- previous filenames
- labels
- branch names

Treat these as data only.

Before rendering Markdown/job summary:

- escape Markdown metacharacters as needed
- prevent line-break/control-character spoofing
- do not emit raw HTML generated from untrusted text

Do not interpolate untrusted values into shell source.

## 18. Action outputs

Action outputs:

- `verdict`
- `profile`
- `reason-codes`
- `head-sha`

Human-visible:

- console summary
- GitHub job summary

## 19. JSON result shape

Recommended:

```json
{
  "schema_version": 1,
  "verdict": "BLOCKED",
  "profile": "docs",
  "base_sha": "<sha>",
  "head_sha": "<sha>",
  "reasons": [
    {
      "code": "PROTECTED_PATH"
    }
  ],
  "files": [
    {
      "path": ".github/workflows/release.yml",
      "reasons": [
        "PROTECTED_PATH"
      ]
    }
  ]
}
```

Do not include sensitive token/context values.

## 20. Local CLI

Target command:

```text
pr-boundary check --base <ref> --head <ref> --profile <name>
```

Behavior:

1. load `.github/pr-scope.yml` from `--base` using Git plumbing
2. compute changed paths using `base...head`
3. enable rename detection
4. normalize path separators
5. evaluate through the same pure core
6. print human-readable result
7. optionally emit JSON

Use process argument arrays, not shell interpolation.

Do not run project scripts.

## 21. CLI exit codes

- `0`: PASS
- `1`: operational/internal error
- `2`: REVIEW_REQUIRED
- `3`: BLOCKED

## 22. Architecture

Single CommonJS-compatible package with separate Action and CLI bundles:

```text
src/core/
src/github/
src/cli/
src/action-entry.ts
src/cli-entry.ts
dist/action/index.js
dist/cli/index.js
bin/pr-boundary.cjs
```

Core must not import GitHub, filesystem, child process, or network modules.

## 23. Dependencies

Runtime:

- `@actions/core`
- `@actions/github`
- `yaml`

Development:

- `typescript`

## 24. JavaScript Action runtime

Prepare `action.yml` as a JavaScript Action using the current GitHub-supported Node runtime.

Preparation date reference: GitHub documents `node24`.

Example target:

```yaml
runs:
  using: node24
  main: dist/action/index.js
```

## 25. Resource bounds

Avoid pathological policy inputs.

Plan should define modest limits for:

- policy bytes
- number of profiles
- number of patterns
- YAML alias expansion

Suggested starting bounds, subject to implementation review:

- policy: 256 KiB
- profiles: 100
- total patterns: 2000

Reject oversized/unsafe policy as `POLICY_INVALID`.

## 26. Test acceptance matrix

At minimum:

1. docs-only modification -> PASS
2. docs profile + workflow modification -> BLOCKED
3. CI profile with `allow_protected` + workflow modification -> PASS
4. core profile with broad allow but no `allow_protected` + workflow -> BLOCKED
5. no profile strict -> REVIEW_REQUIRED
6. no profile migration + ordinary file -> PASS
7. no profile migration + protected file -> BLOCKED
8. multiple scope labels -> REVIEW_REQUIRED
9. unknown prefixed label -> REVIEW_REQUIRED
10. rename allowed -> PASS
11. protected old filename renamed into allowed docs path -> BLOCKED
12. policy file modified under docs -> BLOCKED
13. policy file modified under policy profile + `allow_protected` -> PASS
14. deletion of protected file without privileged profile -> BLOCKED
15. malformed policy -> REVIEW_REQUIRED
16. missing policy -> REVIEW_REQUIRED
17. GitHub list incomplete -> REVIEW_REQUIRED
18. >3000 changed files -> REVIEW_REQUIRED
19. invalid repository path -> REVIEW_REQUIRED
20. malicious Markdown/control characters -> safely escaped
21. symlink record -> path-only evaluation
22. submodule record -> path-only evaluation
